## Konteks penting — baca dulu sebelum desain implementasi

ZEVORA **sudah punya** sistem trace asli untuk tool/aksi yang benar-benar dieksekusi:
`AgentTrace.observations` (`agent/core/execution.py`) dan `agent_trace` yang dikirim balik
sebagai bagian metadata pesan (`main.py`, field `agent_trace` di `chat_message`). Ini beda
dengan permintaan user soal `<agentic_log>` — user minta LLM sendiri yang menulis narasi
langkah kerjanya lewat system prompt, gaya "chain of thought tracking".

**Risiko kalau `<agentic_log>` cuma hasil karangan LLM lewat prompt instruction**: LLM bisa
menulis langkah yang terdengar meyakinkan tapi tidak benar-benar terjadi (halusinasi urutan
kerja), apalagi ZEVORA adalah coding agent yang punya akses file/git/terminal — user bisa
salah percaya suatu aksi sudah dilakukan padahal belum. Karena itu, **desain di bawah ini
menggabungkan dua sumber**: narasi dari LLM (`<agentic_log>`) ditampilkan sebagai "ringkasan
niat/reasoning", SEDANGKAN kalau ada tool call/aksi yang benar-benar tercatat di
`agent_trace.observations` untuk request itu, itu WAJIB ditampilkan sebagai entri terpisah yang
ditandai jelas "Verified action" — supaya user bisa bedakan mana narasi LLM dan mana yang benar-benar
tercatat dieksekusi oleh sistem.

## BAGIAN 1 — Backend: system prompt & parsing structured output

File: `main.py` (`TaskRequest.system` default, fungsi `task()` sekitar baris 1451),
`agent/core/execution.py`.

1. Cek dulu bagaimana `system_prompt` sekarang dibentuk (`main.py` baris ~1451,
   `TaskRequest.system` default `'You are a safe, concise personal AI agent.'`, dipanggil dari
   `chat_message()` tanpa override — artinya inilah satu-satunya titik pusat prompt dasar untuk
   chat UI utama). Tambahkan instruksi format berikut ke system prompt (via string tambahan,
   bukan mengganti keseluruhan default, supaya konteks lain seperti skill/project context yang
   sudah digabung tetap jalan):

   ```
   Sebelum menjawab, tuliskan langkah kerja singkat dalam blok <agentic_log>...</agentic_log>
   berisi poin-poin (bukan paragraf) tindakan yang kamu lakukan untuk menyusun jawaban ini.
   Setelah blok itu, tulis jawaban akhir secara normal (boleh markdown/code block).
   Jangan mengklaim menjalankan aksi (baca file, jalankan perintah, ubah kode) di dalam
   <agentic_log> kecuali kamu benar-benar diberi hasil tool observation untuk itu di konteks
   permintaan ini — kalau tidak ada tool observation, tulis langkah sebagai proses berpikir
   ("menganalisis permintaan", "menyusun struktur jawaban"), bukan klaim eksekusi.
   ```
   (Sesuaikan bahasa instruksi ke Inggris/Indonesia konsisten dengan gaya prompt lain di
   `agent/core/planning.py` — cek `planning_system_prompt()` dulu buat referensi gaya
   penulisan instruksi yang sudah dipakai di codebase ini.)

2. **Jangan** minta model menulis tag `<ui_toolbar>` sendiri — itu action UI statis (copy,
   thumbs up/down, regenerate akan selalu tersedia untuk tiap jawaban asisten yang sukses),
   jadi cukup di-render oleh frontend secara otomatis untuk tiap message, tidak perlu model
   yang menentukan lewat output text (mengurangi risiko token attacker/model salah format,
   dan menghemat output token). Kalau ke depan mau per-message toolbar custom (misal pesan
   tertentu tidak boleh di-regenerate), baru pertimbangkan approach dinamis — untuk sekarang
   cukup statis di frontend.

3. Di `task()` (`main.py`), setelah dapat `result['response']` mentah dari model:
   - Ekstrak isi `<agentic_log>...</agentic_log>` dengan regex yang toleran (non-greedy,
     multiline, case-insensitive tag).
   - **Strip tag itu dari `response` yang disimpan ke database dan dikirim sebagai jawaban
     utama** — jangan sampai tag mentah ikut tampil di riwayat chat atau bocor ke markdown
     renderer.
   - Kalau parsing gagal (model tidak ikuti format — ini AKAN terjadi terutama untuk model
     lokal yang lebih kecil, jangan asumsikan semua model taat instruksi), **response utama
     tetap ditampilkan apa adanya, jangan sampai kegagalan parsing membuat jawaban hilang atau
     error**. `agentic_log` boleh kosong/null kalau tidak ada.
   - Simpan hasil parse (`agentic_log: list[str]`) sebagai field baru di metadata pesan,
     gabungkan dengan `agent_trace.observations` yang sudah ada (field terpisah, jangan
     dicampur jadi satu array supaya frontend bisa bedakan sumbernya) — lihat pola field
     metadata yang sudah ada di `chat_message()` (`metadata={key:result.get(key) for key in
     (...)}`), tambahkan `'agentic_log'` ke tuple key itu.
   - Cek skema `workspace_manager.add_exchange()` (`agent/core/workspace.py`) — apakah
     metadata JSON sudah fleksibel menerima field baru tanpa migrasi skema, atau perlu update
     kolom/skema SQLite. Kalau field metadata disimpan sebagai JSON blob, kemungkinan tidak
     perlu migrasi; verifikasi dulu sebelum asumsi.

## BAGIAN 2 — Frontend: render log & toolbar

File: `static/chats.js` (`appendMessage`), `static/markdown.js`, `static/styles.css`.

1. **Render `agentic_log`** sebagai section collapsible di ATAS jawaban utama dalam bubble
   assistant yang sama — pola seperti "reasoning/thinking" disclosure yang umum di Claude/
   ChatGPT (default collapsed atau expanded, judul singkat "Workflow" / "Langkah kerja" dengan
   ikon chevron). Isi list poin-poin dari `agentic_log`. Kalau ada entri dari
   `agent_trace.observations` (tool call sungguhan) untuk request itu, tampilkan sebagai
   sub-list terpisah dengan label jelas "Verified actions" + ikon centang, dibedakan visual
   dari narasi LLM (misal warna/opacity beda) — supaya user tidak salah kira semua baris
   di log itu benar-benar dieksekusi sistem.
2. Kalau `agentic_log` kosong/tidak ada (model tidak ikuti format, atau fitur baru dinyalakan
   sebelum pesan lama ada), **jangan tampilkan section kosong** — sembunyikan section itu sama
   sekali untuk pesan tersebut, jangan tampilkan placeholder "no log available" yang mengganggu.
3. **Toolbar per-message** (`copy`, `thumbs_up`, `thumbs_down`, `regenerate`) — tambahkan baris
   ikon kecil di bawah tiap bubble assistant (sukses, bukan error — error sudah punya tombol
   "Try again" sendiri, jangan duplikasi):
   - **Copy**: salin teks jawaban (markdown mentah atau plain text — tentukan salah satu,
     disarankan markdown mentah supaya kalau di-paste ke editor lain formatnya ikut).
   - **Regenerate**: re-submit request yang sama seperti pola `retry` yang sudah ada di
     `chat.js` untuk error bubble — reuse fungsi itu, jangan tulis ulang logic baru.
   - **Thumbs up/down**: ini perlu endpoint baru di backend untuk menyimpan feedback (belum
     ada sebelumnya — cek dulu dengan grep `feedback` di `main.py` dan `agent/core/workspace.py`
     supaya tidak duplikasi kalau ternyata sudah ada kolom terkait yang belum dipakai).
     Tambahkan endpoint `POST /api/chats/{chat_id}/messages/{message_id}/feedback` dengan body
     `{rating: 'up'|'down'}`, simpan ke kolom baru di `workspace.db` (atau tabel terpisah kalau
     mau simpan riwayat perubahan rating). Setelah user klik, tombol berubah state (misal jadi
     terisi/highlighted) dan tidak collapsible balik ke netral kecuali klik ulang tombol yang
     sama (toggle).
4. Icon-only dengan tooltip (bukan tombol berlabel teks panjang) supaya konsisten dengan
   toolbar composer yang sudah dibuat minimal sebelumnya — pakai style icon yang sama.
